Chapter Ten

The Cache Dilemma

Which one, why, and at what cost?
❦ ❦ ❦
for architects • 10+ yrs • tired of vendor decks

"There are only two hard things in Computer Science:
cache invalidation and naming things." — Phil Karlton, via Martin Fowler

Every architect eventually ends up in this meeting. Product has asked why the dashboard is slow. Engineering has proposed "caching." Management has nodded and asked "how much?" — meaning, how long will it take and how much will it cost. You, the architect, are the one person in the room who knows the honest answer: it depends.

This chapter is the map you wish you'd had the first three times you answered "it depends." We're not going to explain what a cache is. You know. We're going to look at the six canonical patterns, the tradeoff axes that matter, the operational failure modes nobody mentions in the vendor deck, and the decision framework that will get you out of the meeting alive.

Along the way, we'll lean on the people who have already made every mistake for us — Phil Karlton's famous quote, the AWS Builders' Library's brutal honesty about "cache addiction," Facebook's 2013 Memcached paper (still the single best production-caching paper ever written), and the AWS ElastiCache whitepaper. Citations at the end. Do read them.

A cache is a performance optimization that also happens to be a distributed systems problem, a consistency problem, a capacity-planning problem, and — if you're unlucky — an availability problem.

§ 10.1First, a harder question

Do you actually need a cache?

Aaji आजी (unburdened by résumé-driven development)

Beta, before you add Redis to the architecture diagram — have you tried just adding an index to the database?

Aaji is right. Far too often, "we need a cache" turns out to mean "we have an unindexed query on a 40-million-row table." Fix that first. The database you already have, tuned correctly, will outperform a poorly-designed cache.

A cache is worth it when, and only when, you have established all four of the following:

  • The same data is read many times more often than it's written (read/write ratio of at least 10:1, ideally 100:1+).
  • The data is expensive to compute or fetch — a complex join, an external API call, an ML inference.
  • The data tolerates staleness within some defined bound. "Stock ticker updated once per second" is fine. "Account balance" usually is not.
  • The access pattern is skewed — there's a hot set smaller than your memory budget. If every key is equally likely, you're just building a slower database.
From the experts

The AWS Builders' Library warns explicitly about this failure mode, describing a service that "becomes addicted to its cache" — where the cache is inadvertently promoted from a helpful optimization to a critical availability dependency. When the cache goes cold, downstream systems, now scaled down, collapse under the restored load.

— AWS Builders' Library, "Caching Challenges and Strategies"

The question is never just "should we cache?" It's "if this cache disappears at 2 AM on a Friday, will the system survive?" If the honest answer is no, you haven't added a cache. You've added a new single point of failure and written "cache" on it.

§ 10.2The Six Patterns

Every caching decision you'll ever make is a remix of these.

There are really only six patterns. Every architecture deck you'll ever see is some combination of them. The AWS ElastiCache whitepaper, Redis's own docs, and CodeAhoy's widely-cited breakdown all converge on this list:

Cache-Aside (the default, and why)

Why cache-aside is the default: it is the only pattern where your system continues to function, correctly, when the cache disappears. The application degrades to "just a regular database-backed service." Slow, yes. Broken, no.

// Cache-aside in Spring — the pattern, not the annotation
public Product getProduct(String sku) {
    String key = "product:" + sku;

    Product cached = redis.get(key, Product.class);
    if (cached != null) return cached;

    Product fresh = productRepository.findBySku(sku)
        .orElseThrow(() -> new NotFoundException(sku));

    redis.set(key, fresh, Duration.ofMinutes(15));  // TTL is not optional
    return fresh;
}

// On write — "commit before invalidate" is the critical ordering
@Transactional
public void updatePrice(String sku, BigDecimal newPrice) {
    productRepository.updatePrice(sku, newPrice);   // 1. commit DB
    // tx commits here
    redis.delete("product:" + sku);                 // 2. invalidate cache
}
Subtle but critical

Delete the cache entry; do not update it. Facebook's Memcached paper (Nishtala et al., NSDI 2013) makes this argument explicit: if two writers race, whichever one sets the cache value last wins — but that write may not correspond to the last database write. Deleting is idempotent; the next read reloads from the source of truth. "Commit before invalidate" is the ordering that matters — reverse it, and a concurrent reader can cache the old value indefinitely.

Write-Through: consistency at the cost of latency

Tanvi तन्वी

Dada, if write-through is "more consistent," why isn't it the default?

Dada दादा

Two reasons. One, your write latency roughly doubles — every write is now DB + cache synchronously. Fine for 100 writes/sec. Painful at 10,000. Two, you're caching data that may never be read. You just paid to cache it anyway.

Use write-through for the narrow cases where strong read-after-write matters and writes are infrequent. Not as a general policy.

Write-Behind: the pattern that eats your writes

Write to cache, ack the user, asynchronously flush to DB. Beautifully low write latency. Also: if the cache node dies with a dirty buffer, those writes are gone. At any scale where this matters, you need durability (AOF, replication, WAL) — at which point you've reinvented a database with worse tooling.

Architect's warning Write-behind for financial, regulatory, or audit data is malpractice. If you cannot answer "what happens if this Redis pod dies right now" with something other than "users notice," do not use write-behind.

§ 10.3Where does the cache live?

Local, distributed, near-cache, multi-tier — a locality decision, not a technology one.

L1 — In-process (Caffeine)

Fastest possible. Nanoseconds. No network. No serialization. Perfect for small, hot, idempotent lookups: feature flags, currency codes, reference data, config. Caffeine is the reference implementation — W-TinyLFU eviction, adaptive sizing.

Costs: one copy per pod. Ten pods = ten cold starts on deploy. Invalidation across pods is your problem (Redis pub/sub, Kafka topic, or just accept a short TTL). Memory competes with your JVM heap.

L2 — Distributed (Redis, Memcached)

Sub-millisecond access. Shared across all pods. Survives deploys. Redis is the default choice today — rich data structures, Lua, streams, persistence options. Memcached is simpler, faster at pure KV, truly stateless (the original Facebook paper runs on this).

Costs: it is a network hop. It is a real piece of infrastructure — HA, replication, failover, version upgrades, capacity planning. It is a new place the system can fail.

Near-cache (L1 + L2 hybrid)

The Hazelcast / Apache Ignite pattern. Keep a small L1 per pod, backed by an L2 cluster that invalidates L1 entries on writes. Serves local reads in nanoseconds; survives pod restarts via L2 warm-up; still shares state across the fleet.

Expert's view

Redis's own architecture team recommends combining tiers rather than picking one: framework-local caches for sub-ms local reads, Redis for cross-service state. A real production payments platform they cite handles "over 10 million transactions across more than 50 microservices" via a tiered model — no single cache would have sufficed.

— Redis Engineering Blog, "Why your caching strategies might be holding you back" (2025)

§ 10.4The TTL is a business decision

The number that nobody wants to own, and which decides everything.

Engineers set TTLs like they set log levels — by copying from the last project. This is wrong. TTL is the operational expression of your staleness tolerance, and that tolerance comes from product, not from code.

Data type Acceptable staleness TTL
FX rates (indicative)30 seconds30s
Product catalog / description5 minutes5m
User profile1 minute, or event-invalidated60s + pub/sub
Account balancezero — don't cachen/a
Reference data (country codes)24 hours1d + manual flush
Homepage layout (anonymous)1 minute60s

Soft TTL + Hard TTL (the AWS IAM pattern)

One of the most underused tricks in caching. Two TTLs per entry:

  • Soft TTL — after this, try to refresh. If refresh fails, keep serving the current value.
  • Hard TTL — after this, the value is forcibly expired no matter what.

This is how AWS IAM clients survive transient identity service brownouts — clients keep serving slightly stale auth data from cache while the upstream recovers, instead of cascading a failure. It's the single best pattern for protecting yourself from downstream outages.

// Using Caffeine's refresh-after-write (soft TTL) + expire-after-write (hard TTL)
Caffeine.newBuilder()
    .refreshAfterWrite(Duration.ofSeconds(30))   // soft: try to refresh
    .expireAfterWrite(Duration.ofMinutes(5))     // hard: force eviction
    .maximumSize(10_000)
    .build(key -> fetchFromUpstream(key));          // on refresh failure → keep old
Dada's rule The soft/hard TTL pattern turns your cache into a graceful degradation mechanism. When the upstream wobbles, users see slightly stale data instead of a 500. That's almost always the right product call — but it must be a product call, not a sneaky engineering one. Get it in writing.

§ 10.5The Failure Modes Nobody Mentions

This is where 10+ years of experience actually earns its pay.

Thundering Herd (the Facebook problem)

A hot key expires. 5,000 concurrent requests all miss the cache simultaneously. All 5,000 hit the database. The database, which was sized to handle post-cache load, is now handling pre-cache load. It falls over. Users start seeing errors. Now your cache is cold everywhere. Welcome to the cascade.

Mitigations (cheapest to most elaborate):

  • Jittered TTL. Don't set TTL to exactly 300 seconds — set it to 300 + random(0, 30). You've spread the expiration across a window. Takes ten minutes to implement, prevents most stampedes in practice.
  • Request coalescing / single-flight. When 5,000 requests miss, let one go to the DB, make the other 4,999 wait for its result. Guava/Caffeine's LoadingCache does this for free on L1.
  • Leases (Facebook's trick). The cache hands out a token to the first miss; subsequent misses are told "wait, try again in a moment." Facebook's 2013 paper reports this cut peak DB query rates on contested keys from 17K/s to 1.3K/s. Read the paper.
  • Refresh-ahead. Proactively reload hot keys before they expire. You never miss; you just work slightly harder in the background.

Hot Keys (one key breaks everything)

Key access is almost never uniform. The "view count for post X" where X is the one post that just went viral is 90% of your cache traffic. One Redis node melts. The Facebook paper notes that a single key can account for 20% of a server's load — and rehashing it elsewhere after failure can chain-overload the new host.

Defenses: client-side replication (store hot keys in multiple places with random routing), sharded counters (write to counter:X:shard_N, sum on read), gutter pools (Facebook's name for a small dedicated failover pool — so a dead main node doesn't rehash onto an equally-loaded sibling).

Cache Stampede on Cold Start

Deploy. All pods restart. All L1 caches are empty. The first few seconds of traffic go straight to L2 or DB. If you have 10 pods and 10k RPS, that's a brief but real spike. AWS's guidance: prewarm caches before routing traffic — run a script against the new pod that hits the top-N hot keys, then flip the readiness probe to green.

The "Cache Addiction" Antipattern

This is the one the AWS Builders' Library warns about, and it's the one 15-years-experienced architects see most often. Over time:

  • The cache becomes indispensable.
  • The database is scaled down because "the cache handles it."
  • Nobody tests what happens when the cache is cold.
  • One day the cache really does go cold — a mass eviction, a failover, a misconfigured deploy.
  • The database, now undersized for real load, collapses.
Architect's checklist

Once a quarter, run a cold-cache game day. Flush the cache in staging with production-like traffic. Measure what breaks. If the answer is "everything," you haven't built resilience — you've built a dependency. Fix it before production tests the same theory.

Invalidation Race Conditions

The classic: process A reads X from DB (before the update), process B updates X in DB, process B deletes X from cache, process A writes its (now stale) copy to cache. The cache now contains stale data with a fresh TTL. Facebook solved this with leases and versioning; most teams use one of:

  • Double-delete. Delete on write, wait ~50ms, delete again. Ugly but simple. Catches the race in practice.
  • Versioned keys. product:123:v42. Increment version on write; never invalidate, just write under a new key and let old keys expire naturally.
  • CDC invalidation. Use Debezium / MySQL binlog / Postgres logical replication to produce invalidation events from the DB. Facebook does this (their "mcsqueal" pipeline). Adds infrastructure but eliminates the race.
Case Study
A Pune e-commerce platform's Big Billion weekend
#architecture-review

A Koregaon Park-based e-commerce company (call them NukkadKart) scaled their system for a three-day sale. Their architect chose, reasonably:

  • L1 Caffeine for product metadata, 60s TTL, 50k entries per pod
  • L2 Redis Cluster for cart, session, inventory snapshots
  • CDN for product images and the catalog browse pages (anonymous only)

Day 1 went beautifully. Day 2, at 8 PM — peak dinnertime browsing — a single product went viral on social media. Every visitor hit the same product page. The architecture broke in a way nobody had predicted:

The Caffeine L1 cache saved the Redis cluster from half the read load. But every 60 seconds, every pod simultaneously expired the hot key, and every pod simultaneously hit Redis. That one Redis hash slot was saturating. Writes (inventory updates) were queueing behind reads. The inventory service timed out. Orders for other products started failing because the shared inventory client was blocked.

Three fixes shipped during the incident:

  1. Added per-pod TTL jitter (60s + random(0, 15s)). Thundering-herd spike flattened immediately.
  2. Moved the hot product into a replicated pool — two Redis masters, client-side random routing. Load on any one node dropped by half.
  3. Added a separate Hystrix/Resilience4j bulkhead for inventory calls so a slow inventory read couldn't starve the rest of the checkout path.

The post-mortem called out what the architect now calls the "hot key blindspot": every performance test had used evenly distributed keys. Real production traffic is never evenly distributed. Load tests with Zipf-distributed keys are now part of their release checklist.

§ 10.6The Architect's Decision Framework

One page. Pin it to the wall next to the whiteboard.

Step 1 — Is caching the right answer at all?

If the bottleneck is an unindexed query, a chatty API call, or an N+1 — fix that first. A cache will hide the problem, not solve it, and you'll pay for the hiding place every single month.

Step 2 — What is the staleness tolerance?

Get a number from product. In seconds. In writing. If they say "it must be real-time" ask what they mean. If they say "live," ask what they mean. If they can't give you a number, they don't need a cache yet.

Step 3 — What is the access pattern?

  • Read-heavy, uniform keys: cache-aside + L2 (Redis).
  • Read-heavy, hot keys: cache-aside + L1 (Caffeine) + L2, with replicated hot-key pool and jittered TTL.
  • Write-heavy, read-rarely: write-around. Don't pollute the cache.
  • Write-heavy, read-after-write matters: write-through on the narrow set of keys that need it. Cache-aside on the rest.
  • Write-heavy, loss-tolerant: write-behind with durable backing — but question why you need this before choosing it.

Step 4 — What is the failure behaviour?

Write it down. If the cache dies:

  • Does the system still work? (If not → redesign.)
  • What's the latency under all-miss conditions? Is that SLO-acceptable for 10 minutes? For an hour?
  • Is there a stampede-protection pattern in place? (Leases, request coalescing, jitter.)
  • When did you last test the cold-cache scenario?

Step 5 — What is the cost of being wrong?

A stale product description is a support ticket. A stale account balance is a regulatory filing. A stale fraud score is a breach. Calibrate ambition to consequence. If the data is load-bearing, do not cache it aggressively — or, better, do not cache it at all.

§ 10.7The Gallery of Regret

Production incidents, anonymised, offered as a public service.

1   The uniform TTL — sab ek saath expire

Every key cached with exactly 5-minute TTL. Every 5 minutes, 40% of the cache expires simultaneously. Database sees a textbook sawtooth load pattern. Fix: jitter the TTL. Five minutes of work, years of relief.

2   The cache as source of truth — bas yahi sach hai

Someone wrote the user's updated email only to Redis. Redis failed over; the unreplicated replica became primary; the write was lost. Customer support now thinks this user is a fraud because their recent login "doesn't match." A cache is never a source of truth. The database is. Always.

3   Caching authorization decisions — revoke nahi hua

Permission cached for 10 minutes. HR terminates an employee. For the next 10 minutes, the ex-employee still has access. Auditor discovers this during the quarterly review. Cache authorization only if you have pub/sub invalidation on privilege change, or use very short TTLs (≤30s) with explicit documented risk acceptance.

4   Unbounded cache entries — memory leak with extra steps

Caffeine built without maximumSize. Keyspace: user IDs. Over six months, every user who ever logged in stayed in the cache. 40 GB heap. OOM on a Tuesday. Set a bounded size. Use recordStats(). Look at the hit rate. Tune from data, not from hope.

5   Caching the wrong granularity — poora tiffin cache kar liya

Caching getUserFullProfile() — a 40-field object — when 90% of callers only need name and avatar. Invalidation on any field change clears the entire entry; next 100 reads all miss. Cache at the granularity of what's actually read.

6   Serialisation surprises — Jackson ne dhoka diya

You upgrade Jackson. A polymorphic type changes default serialisation. Keys deployed yesterday can't be read today. Cache returns ClassCastException instead of null. Solution: version your cache keys on schema change (user:v2:123), and catch deserialisation errors as cache misses.

7   The "temporary" cache that became permanent — jugaad ka empire

Added during an incident to mask a slow service. Nobody ever fixed the slow service. Three years later, the slow service cannot be refactored because "everything depends on the cache layer." Every cache should have a ticket for the real fix, a decommission plan, and a date.

§ 10.8The Architect's Checklist

Before signing off on a caching design

Design review — dastkhat karne se pehle

  • Product has signed off on a written staleness tolerance (in seconds)
  • Read/write ratio is measured, not assumed — and is at least 10:1
  • Access pattern is skewed (hot keys identified) or provably uniform
  • Pattern is explicitly chosen: cache-aside / read-through / write-through / etc., with rationale
  • TTLs are jittered to prevent simultaneous expiry
  • Soft TTL + hard TTL used for anything dependent on a downstream service
  • Stampede protection in place — leases, single-flight, or request coalescing
  • Hot-key strategy documented — replication, sharded counters, or "accepted risk"
  • Cache location justified — L1 vs L2 vs both — with memory and network budget
  • Invalidation strategy is explicit — TTL, delete-on-write, versioned keys, or CDC
  • "Commit before invalidate" is the documented ordering for writes
  • Keys are versioned for safe schema/serialisation migration
  • Cold-cache behaviour tested in staging with production-like traffic
  • Hit rate, miss rate, eviction rate, and p99 latency are on a dashboard
  • The cache has a named owner, a runbook, and a decommission plan
  • You can answer: "if Redis dies right now, what happens?"
Chaiwala Bhau (closing philosophy, 5 PM)

Architect sahab, see here — I have 200 cups. Customer orders chai, I pour. Customer orders kadak chai, I pour kadak. But I always know which kettle is fresh and which has been sitting since morning. Tumhara cache bhi aisa hi hona chahiye — har cup ki memory honi chahiye.

Your cache should know what's fresh, what's stale, and when to throw it out. That is all.

The best cache is a conscious one.
It knows what it has, how old it is, and what to do when nobody else is available. — the architect's version of Phil Karlton's joke

Caching is an architecture decision dressed up as a technology one. Redis, Caffeine, Memcached — these are the easy choices. The hard ones are: what to cache, where in the stack, at what granularity, with what staleness, under what failure mode, with what invalidation contract, and who pays when it's wrong.

Answer those six questions before you touch a YAML file. Your future on-call self will thank you.
