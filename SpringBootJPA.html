§ 6.1The N+1 समस्या

Death by a Thousand Queries, or: IRCTC at 10:00:01 AM

You know Tatkal booking. 10 AM sharp. You've filled the passenger details, you've got your UPI ready, you click "Book Now" — and then spin, spin, spin, error. The IRCTC team, to their credit, have made enormous strides in recent years. But in the old days, one common failure mode was simple: a request that should have been one database query was actually four hundred.

Your code is doing the same thing. Right now.

Case Study
The Swiggy-Style Order Dashboard
#real-world

A mid-sized Pune food-delivery startup — let's call them QuickBhook — built an internal operations dashboard showing all live orders. Each row needed the customer name, the restaurant name, and the delivery partner's name. The developer wrote, proudly:

// three lazy fields, one loop, four hundred rows
List<Order> orders = orderRepo.findAllByStatus(ACTIVE);
return orders.stream().map(o -> new Row(
    o.getCustomer().getName(),      // +1 query
    o.getRestaurant().getName(),    // +1 query
    o.getDeliveryPartner().getName()// +1 query
)).toList();

On a dev machine with 12 orders, it loaded in 80 milliseconds. On the first production Friday night — a rainy Pune evening, peak dinner rush — the same endpoint tried to do 1,201 queries per dashboard refresh. Every ops person refreshing every 10 seconds.

The fix took two lines. A single JPQL query with JOIN FETCH, returning a DTO. Response time dropped to 120ms. The ops team stopped filing tickets. The CTO stopped having opinions about the backend team.

The Fix

☠ Nahi karne ka

Let Hibernate lazy-load its way into your next postmortem.

✦ Aise karo

Tell JPA exactly what you want, exactly once.

// DON'T — looks innocent, isn't
public List<OrderSummary> summaries() {
    return orderRepo.findAll().stream()
        .map(o -> new OrderSummary(o.getId(), o.getCustomer().getName()))
        //                             ^ LAZY FETCH. ONE QUERY PER ORDER.
        .toList();
}

// DO — one query, grown-up behaviour
@Query("""
    SELECT new com.quickbhook.OrderSummary(o.id, c.name, r.name, p.name)
    FROM Order o
    JOIN o.customer c
    JOIN o.restaurant r
    JOIN o.deliveryPartner p
    WHERE o.status = :status
    """)
List<OrderSummary> findActiveSummaries(@Param("status") Status status);
Dada's tip Write an integration test that counts SQL statements using hibernate.getStatistics(). Fail the build if a known endpoint exceeds its query budget. N+1 doesn't announce itself in code review — it announces itself during the CEO demo.

§ 6.2Open Session In View

The Setting That Ate Your Long Weekend

Spring Boot, being a helpful boy, turns on a setting called spring.jpa.open-in-view by default. It means well. It keeps your Hibernate session open for the entire HTTP request — through the controller, through JSON rendering, through the network send to the client.

It is the rishtedar who came for Diwali and is still on your sofa in January. You were polite at first. You are no longer polite. But they are comfortable, and they are holding your last database connection hostage.

Aaji आजी (asking the real questions)

Beta, if you are not using the connection, why are you holding it? In my time, if you held the phone line for four hours, your brother-in-law would hear about it.

Now imagine you have a HikariCP pool of 20 connections, each HTTP request holds one for 800ms (because your mobile user is on 3G in a basement in Kothrud), and suddenly 500 requests arrive per second. The math does not work. The math never works. The math is why you are on-call.

The fix is one line of YAML.

# application.yml — first thing you add to every new service
spring:
  jpa:
    open-in-view: false   # always. forever. no exceptions.
Real horror story A Pune-based payments team turned this off exactly once. The service threw 14 LazyInitializationExceptions they had been unknowingly ignoring for 18 months. The "workaround" had been a note in the admin panel that said "please don't click that button." The compliance team had been clicking that button. Daily.

§ 6.3Entities Are Not DTOs

A Serialization Tragedy in Three Acts

Picture this. You return a JPA entity directly from your controller, because why not, it has all the data right there. Jackson begins to serialize it. The Order has a customer, who has a List<Order>, and each of those orders has a customer, who has a List<Order>, and —

Even if you survive with @JsonIgnore, you've now welded your API contract to your database schema. When the DBA renames a column, the Android app breaks at 11 PM on a Saturday. When the iOS team needs a new field, you touch your database. Mubarak ho — you've built a distributed monolith with extra steps.

// DON'T — entity going out over the wire
@GetMapping("/orders/{id}")
public OrderEntity get(@PathVariable UUID id) {
    return orderRepo.findById(id).orElseThrow();
}

// DO — purpose-built DTO, API-shaped
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable UUID id) {
    return orderService.findById(id);
}

public record OrderResponse(
    UUID id,
    BigDecimal amount,
    String currency,
    String customerName,
    Instant placedAt
) {}

§ 6.4@Transactional

Kahan lagana hai, kahan nahi

The Three Sins of @Transactional

Sin the first: calling a @Transactional method from inside the same class. Spring's proxy does not intercept same-class calls. Your annotation is a decoration. It is, at best, aspirational.

Sin the second: putting it on the controller. The controller should not know what a transaction is. Also, if an exception escapes your error handler, you are now rendering an error response inside a doomed transaction. Very exciting.

Sin the third — and this is the big one: calling Kafka, HTTP, email, the fraud API, or PayGlocal-whoever from inside a transaction. You are now holding database row locks while waiting for someone else's server to respond. If their server is slow, your database is slow. If their server is down, so are you.

Case Study
The UPI-Style Payment That Deadlocked Everything
#payments

A fintech in Viman Nagar processes UPI-like payment intents. Their submit flow was, roughly:

@Transactional
public PaymentResult submit(PaymentCommand cmd) {
    Payment p = paymentRepo.save(Payment.from(cmd));
    fraudClient.check(p);                    // HTTP → fraud service, 1.2s avg
    notificationClient.sendSms(p);           // HTTP → SMS provider, 600ms
    kafkaTemplate.send("payments", p.asEvent()); // sync Kafka send
    return PaymentResult.accepted(p);
}

On a normal Tuesday: fine. On a Friday evening when the SMS provider had a regional outage and calls started taking 30 seconds to time out: the DB connection pool exhausted in 90 seconds. Every payment submission was holding a locked row on the payment_idempotency table, waiting for an SMS they would never successfully send.

The fix was the transactional outbox pattern. Inside the transaction, save the payment and write an outbox_event row. Commit. A separate background worker reads the outbox and does the actual HTTP / Kafka / SMS work. The transaction holds a DB lock for milliseconds, not half a minute. The next SMS provider outage came and went; nobody noticed.

@Transactional
public PaymentResult submit(PaymentCommand cmd) {
    Payment p = paymentRepo.save(Payment.from(cmd));
    outboxRepo.save(OutboxEvent.paymentSubmitted(p));   // same tx
    // NO network calls here
    return PaymentResult.accepted(p);
}
// A separate @Scheduled poller (or Debezium CDC) drains the outbox
// and makes the actual HTTP / Kafka / SMS calls. Retries. Idempotent.
Dada's rule A transaction is a database thing, not a business thing. It starts when you need to change data, ends when you have changed it, and lasts as briefly as it possibly can. Anything longer is borrowing trouble.

§ 6.5Lombok + JPA

A Love Story That Ends in StackOverflowError

You put @Data on your JPA entity. Lombok happily generates equals(), hashCode(), and toString(). These dutifully reference every field. Including the List<Child> which references its parent, which references the list, which references —

Bugasur बगासुर (cackling from the stack trace)

MUAHAHA! Maine toString call kiya aur tumhari JVM 47,000 lines print karke reh gayi! Your logger is now writing the great Indian epic to stdout!

☠ Don't
@Data
@Entity
public class Customer {
  @Id UUID id;
  @OneToMany
  List<Order> orders;
}
// toString → infinite loop
// equals → loads full graph
✦ Do
@Getter @Setter
@Entity
public class Customer {
  @Id UUID id;
  @OneToMany
  List<Order> orders;

  // equals/hashCode by @Id only
}

Equality for entities is based on the identifier, not the field graph. Two Customer instances with the same ID are the same customer, even if one has a stale email and the other has the latest. Write your own equals/hashCode based on ID alone. It is six lines. It is worth it.

§ 6.6The Gallery of Horrors

Mistakes we have, personally, shipped to production

1   save() in a loop — ek ek karke

You iterate 10,000 rows and call repository.save() each time. Each save is its own flush, its own round trip, its own tiny heartbreak. Use saveAll() with hibernate.jdbc.batch_size=50, or skip JPA for bulk work and use JDBC. Your 40-minute nightly import becomes 40 seconds. Your batch job stops being on the morning standup agenda.

2   No @Version — lost updates ki kahaani

Two ops users update the same customer record at the same time from different screens. The second write silently overwrites the first. Your integration tests are green. Your user is in the hold queue complaining their KYC status reverted. Add @Version Long version, handle OptimisticLockException, tell the user to retry.

3   CascadeType.ALL by default — jo ek ka, wahi sab ka

You delete a customer. Cascade deletes every order. Cascade deletes every payment. Cascade deletes every audit log. The RBI auditor calls. CascadeType.ALL is not a default; it is a decision. Declare cascades per-relationship, and never for anything audit-bearing.

4   findById → modify → save — teesra step bekar hai

Inside a transaction, entities loaded are already managed. Modifying a field is enough — Hibernate dirty-checks on commit. The explicit save() is theatre. It doesn't hurt, but it's also the reason the next dev thinks save() means "persist now." It does not.

5   @ManyToMany without a join entity — kal pachtaoge

The join table has no fields today. Next sprint, product needs an addedBy column and a addedAt timestamp. Now you're doing a schema migration on 40 million rows at 11 PM on a Thursday. Model the join as its own entity from day one. Always.

6   Forgetting readOnly = true — replica ka kaam primary pe

Read queries marked @Transactional(readOnly = true) skip Hibernate's dirty-check machinery and can be routed to read replicas. Most people never set it. Most people then wonder why their read traffic hammers the primary database into submission during Big Billion Day.

7   Logging the entity — PAN card with your morning logs

log.info("saved customer: {}", customer) — where customer helpfully triggers lazy loads of every relationship AND prints the PAN, Aadhaar, and IBAN into Splunk. Now it's 2 AM, compliance wants the logs purged, and you're writing a data-breach report on Diwali weekend. Mask with a Jackson mixin. Override toString(). Do not — ever — log the whole entity.

§ 6.7The Survival Checklist

Pin it above your monitor. Tape it to the fridge.

Before merging any JPA code — merge karne se pehle

  • spring.jpa.open-in-view: false is set in your YAML
  • No entity leaves the service layer — DTOs or records only
  • Every fetch has an explicit strategy (JOIN FETCH, @EntityGraph, or a separate query)
  • Query count is tested for list endpoints — a budget, not a wish
  • @Transactional is on the service, never on controllers or private methods
  • No HTTP, Kafka, email, or external API calls inside any transaction
  • Read-only queries are marked readOnly = true
  • @Version is present on any entity updatable by more than one actor
  • No @Data on entities — @Getter @Setter with ID-based equals/hashCode
  • Bulk writes use saveAll() + batching, not save() in a loop
  • Cascades declared per-relationship, never CascadeType.ALL by habit
  • No entity is logged via toString() — PII and lazy loads are waiting to bite
